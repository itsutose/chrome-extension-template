# 1. ワークスペースは必ずchrome-extension-vite-sampleディレクトリ直下で開くこと
- launch.jsonのパス解決やデバッグ設定の認識に影響するため。

# 2. デバッグ設定（.vscode/launch.json）はワークスペース直下のものを使用すること
- Cursor/VSCodeはワークスペース直下の.vscode/launch.jsonのみを認識する。

# 3. Braveブラウザでの開発・デバッグを推奨する
- 企業管理Chromeの制限を回避し、自由な開発・デバッグが可能。

# 4. Braveは./start-brave-debug.shでデバッグモード起動すること
- remote-debugging-port=9222で起動し、アタッチデバッグが可能になる。

# 5. デバッグ時は「Attach to Brave Extension」または「Launch Brave Extension」を選択すること
- launch.jsonに複数のデバッグ構成を用意している。

# 6. launch.jsonのパス指定はワークスペース階層に合わせて調整すること
- ワークスペースの開き方で${workspaceFolder}の意味が変わるため。

# 7. 企業管理ChromeではなくBraveで拡張機能をテスト・デバッグすること
- 企業管理Chromeでは拡張機能のインストールやデバッグが制限される。

# 8. ホットリロード・TypeScript・React・ソースマップを有効にして開発すること
- 開発効率とデバッグ性を高めるため。

# 9. トラブル時はREADMEのトラブルシューティングを参照すること
- 代表的な問題と解決策をREADMEにまとめている。

# 10. ワークスペースファイル（chrome-extension.code-workspace）も活用可能とする
- 複数人開発やエディタ設定共有に便利。

# 11. ルールや経緯は.cursor/rules_background/chrome-extension.mdに記載すること
- ルールと背景を1対1で管理しやすくするため。

# 12. 新しい開発者・エージェントは必ずこのルールを最初に確認すること
- 環境構築や運用ミスを防ぐため。

# 13. ルールに変更があった場合は必ず背景ファイルも更新すること
- ルールと背景の整合性を保つため。

# 14. 重要な運用ノウハウ・注意点はREADMEにも明記すること
- 新規参画者が最初に目を通すため。

# 15. 企業管理Chromeの制限回避策としてBraveを選択した経緯を背景ファイルに記載すること
- なぜBraveを使うのかを明確に伝えるため。

# 16. launch.jsonのwebRootやruntimeArgsのパスはワークスペース階層依存であることを明記すること
- パス解決ミスによるデバッグ失敗を防ぐため。

# 17. デバッグ設定が認識されない場合はワークスペース階層を見直すこと
- 多くのトラブルが階層ミスに起因するため。

# 18. Braveのパスやビルド状況もトラブル時に確認すること
- Braveのインストールパスやdistのビルド漏れが原因の場合がある。

# 19. ルールファイルは25行以内を目安とし、肥大化時は分割すること
- 管理しやすくするため。

# 20. ルールと背景ファイルの命令・見出しは1対1で対応させること
- 追跡性・可読性を高めるため。

# 21. ルール策定時は.cursor/rules_background/chrome-extension.mdに経緯・実例を記載すること
- ルールの背景や実際の運用例を残すため。

# 22. ルールファイルのフロントマターはAuto Attachedを意識して設定すること
- Cursorの自動適用を促進するため。

# 23. ルールの変更・追加時は必ず全体の整合性を確認すること
- ルール間の矛盾や重複を防ぐため。

# 24. ルールの記載例・書き方はhttps://docs.cursor.com/context/rules を参照すること
- Cursorルールの最新仕様に準拠するため。

# 25. ルールは日本語で記載すること
- 日本語話者の開発者が迷わないようにするため。
